# Ooznest Control Duet comparison

This compares the current Duet source checkout with stock Ooznest Control at its fork point, commit `f19be69`, and with the legacy WorkBee Control interface supplied with Duet-based WorkBees. Bench results refer to a Duet 2 Ethernet running RepRapFirmware 3.3, connected by HTTP and by USB on COM22. WorkBee Control parity is based on the legacy screens provided for review, the public project, and Duet documentation. It is a workflow comparison, with live verification called out separately.

## Changes from stock Ooznest Control

| Area | Stock Ooznest Control | Ooznest Control Duet |
| --- | --- | --- |
| App and layout | grblHAL sender with the Ooznest sidebar, 3D preview, editor, Probe, Macros, SD Card, Tools, Console, Settings and Troubleshooting. | Forks the existing app and keeps its startup path and main layout. Uses Duet branding and shows firmware-appropriate controls in those same views. |
| Desktop connection | USB and network transports selected from the existing Connect dialog. | USB plus WiFi/Ethernet via the Duet HTTP API. The address field defaults to the factory value `192.168.251.2`, accepts a saved address, and uses HTTP port 80 by default. The legacy Telnet port field is hidden. Electron uses a native HTTP bridge. |
| Browser connection | Sidebar Connect opens the Web Serial picker in supported browsers. | Same direct picker flow, followed by Duet firmware detection and serial status queries. USB access errors are shown in the app. Browser HTTP depends on the browser and the controller allowing the requesting origin. |
| Machine feedback | grblHAL status reports drive positions, state, overrides and signals. | Duet HTTP status and its object model drive machine/work positions, homing, probe input, feed override and job feedback. Serial supplies live state and position through RepRapFirmware queries. |
| Machine controls | grblHAL jogging, homing, zeroing, WCS and real-time overrides. | Uses RepRapFirmware commands through the existing DROs and jog card. Duet uses incremental jogging, adds Z babystepping, and exposes Duet emergency stop and feed override. grblHAL-only controls are hidden where they have no Duet equivalent. |
| Jobs and preview | Sender job controls, G-code editor and 3D viewer with grblHAL SD support. | Keeps the editor, viewer and job controls. Over HTTP, jobs can be loaded from the Duet SD card into the preview, uploaded and started, or run directly. The app can load the active SD job and clear the preview without deleting the file. Job progress comes from the controller. Power Loss Resume is exposed when applicable. |
| SD card | grblHAL SD workflows. | Duet Jobs and System folders use the HTTP file API. The app supports browsing, creating folders, uploading, downloading, renaming and deleting. System files can be edited and saved through the existing editor. |
| Probing | Ooznest Probe panel with grblHAL probing routines and Config Wizard integration. | Keeps the Probe panel, plate settings, Single Surface and Outside Corner controls. Supported routines use a Duet SD macro and check controller state before starting. Duet hides the Config Wizard banner and grblHAL-specific routines such as tool-length, center, rotation and inside corner probing. |
| Macros | Sender macros stored in the app and sent as commands. | Keeps sender macros. Over HTTP, the new SD Macros section above them lists `0:/macros`, browses folders and confirms before running a file with `M98` on the controller. Live execution of this addition is pending. |
| Settings | Searchable, grouped grblHAL settings, inline editing and a shared Save action. | Uses the same sidebar, search and row-editing pattern for Duet settings. Axis rows include travel and steps/mm. The second Y motor appears as Ganged Y-motor travel resolution. The model preset fills travel rows for review. HTTP Save can apply changes and save the applicable WorkBee startup files. USB axis writes are session-only. |
| Network setup | grblHAL networking settings and firmware-specific services. | USB can read the Duet address, enable the existing Ethernet interface and request static IP or DHCP for the current session. The applicable WorkBee startup configuration can be edited over HTTP for persistence. Wi-Fi provisioning remains manual. |
| Troubleshooting | grblHAL build information, homing, signals and diagnostic export. | The existing Troubleshooting view shows Duet board and firmware info, app transport, controller address when available, homing and supported diagnostics. |
| Packaging | Ooznest Control app identity and build targets. | Separate Duet app identity for desktop, web and Cordova. Windows Electron is the live bench-tested target. Android has booted in an emulator. Physical Android USB and HTTP remain unverified. |

## Parity with legacy WorkBee Control

WorkBee Control runs as a controller-hosted Duet Web Control variant. Its repository describes standalone SD and SBC builds across several Duet boards. The Duet sender's live test coverage is narrower and centers on the standalone Duet 2 Ethernet and RepRapFirmware 3.3. [WorkBee Control repository](https://github.com/Ooznest/WorkBee-Control)

| Legacy workflow | Where it lives in Ooznest Control Duet | Parity and evidence |
| --- | --- | --- |
| Open the controller web UI | Connect → WiFi/Ethernet in Electron, or connect through USB for setup and diagnostics. | HTTP and COM22 verified on the same board. The desktop app can read the USB-discovered address and use it for HTTP reconnect. Browser-hosted HTTP, Wi-Fi hardware and SBC compatibility remain unverified. |
| Send G-code and read replies | Console, with live DROs in the sidebar. | Firmware identification, status and ordered read-only sender macro commands verified over both transports. |
| Home, jog, zero and choose work coordinates | Sidebar DROs and incremental jog card. | Homing state and coordinate readback verified. HTTP WCS selection and restoration verified. Physical homing, jog direction and distance, and zeroing require a powered machine. |
| View job progress and preview | Existing job progress display, 3D Preview and Editor. | A dwell-only SD job ran on the bench. Electron displayed progress, loaded the live job into the preview, and unloaded it while preserving the SD file. Uses the Ooznest viewer and editor. |
| Pause, resume, cancel and recover jobs | Existing job controls and Power Loss Resume. | Pause/Resume/Stop controls are implemented. The Off board limits end-to-end testing of the powered job state transitions. Recovery needs a valid saved recovery file and a powered controller. Legacy Auto-Sleep parity is unverified. |
| Browse and manage Jobs and System files | SD Card → Jobs and System. | Temporary upload/download, folder creation/deletion, file rename and system-file editing were checked over HTTP. System editing uses the existing Ooznest editor. |
| Browse and run SD macros | Macros → SD Macros, above sender macros. | Browse and confirm behavior follows Duet Web Control's macro workflow. The controller receives a file run command. Live execution and legacy macro file-management parity are unverified. [Duet Web Control manual](https://docs.duet3d.com/en/User_manual/Reference/Duet_Web_Control_Manual#macros) |
| Probe a surface or outside corner | Probe → Single Surface, Outside Corner and Probe Configuration. | Uses the existing Ooznest controls and Duet probe commands. Automated tests cover the generated sequences and missed-touch handling. Electron verified the Off board rejects probing before upload or motion. Physical contact, travel, offsets, retract and cleanup remain to be checked. |
| Adjust feed override and Z offset | Sidebar feed override and Z babystepping. | Feed override change and restoration verified on the bench. Z offset display verified. Physical babystepping remains pending. |
| Display spindle state | Duet spindle display and settings. | Verified on a board reporting no configured spindle. A configured spindle is needed to verify active state and RPM display. |
| Set work area and steps/mm | Settings → Axes, with X, Y and Z groups and one Save button. | Live readback verified over HTTP and COM22. COM22 displayed 270 mm Y travel and 400 steps/mm for the ganged Y motor. Both transports reject axis writes while Off. Successful apply and HTTP persistence after restart remain pending. |
| Set communication options and inspect sensors | Settings → Communications and Troubleshooting. | The HTTP polling delay is configurable. Firmware and homing readback were verified. Full legacy communication and sensor-panel parity has not been established. |

## Verification summary

The source Electron window was visually checked at startup and through macro dialog open and close. Live bench checks cover HTTP operations, COM22 detection and status, settings readback, and USB-to-HTTP reconnect. The current automated suite has 37 tests. Recent SD Macro browsing and execution, the browser USB picker, and the latest connection-dialog changes have more limited verification than the earlier desktop bench workflows.

The remaining powered checks are jog, home, zero, probe, babystepping, configured spindle, settings persistence, and SD job pause, resume, stop and recovery. Network checks still include DHCP on a network that offers a lease, Wi-Fi provisioning on the appropriate hardware, browser HTTP and physical Android transports. See the [bench verification notes](duet-verification.md) for the individual runs and their limits.
